# ויצמן — ניהול תקציב בניינים

מערכת לניהול הרווחיות של חברת ניהול מבנים: **131 בניינים פעילים**, 24 קטגוריות
עלות מול דמי ניהול, ספקים, וחוזי שירות עם היסטוריית מחירים.

נבנתה מתוך `רשימת בנינים 2025.xlsx` — 4 גיליונות, 41 עמודות, 212 תאי הערות.

| | לחודש | לשנה |
|---|---|---|
| הכנסה | 1,088,983 ₪ | ~13.07M ₪ |
| הוצאות | 940,050.08 ₪ | ~11.28M ₪ |
| **רווח** | **148,932.92 ₪** | **~1.79M ₪** |

## הרעיון בשורה אחת

**שום סכום לא נשמר — הכל נגזר מהחוזים בכל קריאה.**

באקסל הרווח היה מספר שיושב בתא. הוא היה נכון, אבל רק כי מישהו זכר לעדכן אותו.
כאן `profitability.js` מחשב הכל מחדש בכל רינדור: שינוי סכום חוזה מזיז את הסה"כ,
את הרווח, את ה-margin ואת ה-markup באותו רגע. פירוק הקטגוריות והסה"כ נגזרים
מאותם חוזים ולכן **חייבים** להתאזן — ויש בדיקה שנועלת את זה.

## הרצה — שתי דרכים

### א. בלי להתקין כלום (מומלץ לשימוש יומיומי)

`npm run build:standalone` מייצר **קובץ HTML אחד** ב-`dist-standalone/index.html`
(~600KB) עם כל הקוד בפנים, כולל SheetJS. לחיצה כפולה פותחת אותו בדפדפן; גוררים
לתוכו את קובץ האקסל והמערכת עולה. **בלי Node, בלי שרת, בלי טרמינל.**

אומת מ-`file://` מקצה לקצה: הייבוא מחזיר את המספרים לשקל, `localStorage` עובד,
הנתונים שורדים רענון, והגיבוי וה-CSV יורדים.

### ב. מהריפו, עם Node

```bash
npm install
npm run import:vitzman    # אקסל → seed/vitzman.json + seed/discrepancies.md
npm run dev               # http://localhost:5193 → "טעינת קובץ" → seed/vitzman.json
npm run smoke             # 220 בדיקות
npm run build
npm run build:standalone  # קובץ HTML בודד
```

בלי `.env` האפליקציה רצה **במצב מקומי** — הנתונים ב-localStorage של הדפדפן,
בלי ענן ובלי התחברות. זה מספיק לחלוטין לעבודה עם 131 הבניינים.

## ⚠ הריפו הזה ציבורי

כדאי `git status` — אם קובץ מ-`seed/` מופיע שם, משהו נשבר.

### שלוש הכרעות מודל שכדאי להכיר

**1. לבניין יש `id`; הכתובת היא תצוגה.**
מקור כל הכאב בגיליון היה שהכתובת שימשה כמפתח. לכן `הר הצופים 7ג` ו-`הר הצופים 7 ג`
היו שני בניינים. במודל: `id` יציב, `address` לתצוגה, ו-`aliases[]` שקולט איותים
חלופיים. `addressKey()` מנרמל להתאמה — אבל **רק מיזוגים ודאיים** מתבצעים
אוטומטית; כל השאר נשאר בדוח הסתירות להכרעה אנושית. ייבוא לא מנחש זהויות.

**2. רשימת בניינים אחת. ארבעת הגיליונות הפכו לשדות.**
`status` · `assignedEmployeeId` · `inIlm` הם שדות על אותה ישות, ולא ארבעה
גיליונות שצריך להצליב ביד. לכן `בן גוריון 1` לא יכול יותר להיות גם פעיל וגם
לא-פעיל, ו"35 בניינים בלי עובד אחראי" הוא באנר במסך במקום ידיעה שאין לאיש.

**3. היסטוריית מחירים היא כמה חוזים, לא שדה.**
27 הערות מסוג "הסכם עלה מ-4650 ל-5500 החל מ-1.7.2022" הפכו לשתי שורות
`serviceContract` עם `effectiveFrom` שונה. `activeContract(contracts, asOf)`
בוחר את התקף — ולכן אפשר לשאול "מה הייתה העלות ביוני 2022" ולקבל תשובה.

## ⚠ ברוטו מול נטו — הרווח שהוצג היה ברוטו

רונן אישר (4.9) ש**דמי הניהול כוללים מע"מ**. ההסכם אומר זאת במפורש
(״הסכום כולל מע"מ כדין״), וכך גם הסכומים בגיליון.

**המשמעות: המע"מ שנגבה מוועדי הבתים אינו הכנסה** — הוא נגבה עבור המדינה
ומועבר אליה. הרווח שנשאר בחברה הוא **126,214 ₪ לחודש** ולא 148,933;
העברה למדינה ~22,719 ₪ לחודש.

⚠ **שולי הרווח באחוזים אינם משתנים** — `(I−C)/I` שווה ל-`(I/k−C/k)/(I/k)`.
13.68% נשאר 13.68%. מה שמשתנה הוא **הרווח בשקלים**, וזה המספר שמתכננים לפיו.
אחוז זהה ורווח שונה בכ-18% הוא בדיוק המקום שקל לטעות בו.

### הגזירה אחידה לספק רגיל ולעוסק פטור — וזה לא מובן מאליו

| | מה משלמים | מה נשאר | נטו |
|---|---|---|---|
| **ספק רגיל** | 1,180 ברוטו | מקזזים 180 | **1,000** |
| **עוסק פטור** | 1,000 בלי מע"מ | אין מה לקזז, אבל הגיליון רשם 1,180 (רעיוני) | **1,000** |

**בשני המקרים: נטו = רשום ÷ 1.18.** זו זהות אמיתית ולא הפשטה נוחה — בלעדיה
היינו חייבים לפצל את החישוב לפי סוג הספק. נעולה בבדיקה.

⚠ **הברוטו נשאר ברירת המחדל.** הוא מה שמתאזן מול הגיליון, מול ההסכמים ומול
מה שרונן מכיר בעל פה. הנטו הוא **עדשה נוספת** בדשבורד, לא החלפה: מספר
שמשנים בו את המשמעות בלי לומר זאת הוא מספר שאי אפשר להצליב מול שום דבר.

## המע"מ הרעיוני — למה לא "תיקנו" אותו

23 הערות בגיליון אומרות *"עוסק פטור — הוסף מע״מ פיקטיבי"*: לספק שלא גובה מע״מ
הוסיפו מע״מ רעיוני כדי שהשוואת עלויות מול ספק רגיל תהיה הוגנת. הצד השני של זה
הוא שהמע״מ הרעיוני **בלוע בתוך ההוצאה** ולכן מקטין את הרווח המדווח.

הפיתוי היה לגזור לאחור את הסכום הנקי ולהציג רווח "מתוקן". לא עשינו את זה:
אף הערה לא מתעדת את הסכום שלפני ההוספה, ולכן כל גזירה היא המצאת נתון.
מה שכן: הסכומים נשמרו **כפי שהם בגיליון** (ולכן המערכת מתאזנת לשקל מול האקסל),
הרכיב הרעיוני מוצג בנפרד **מסומן כאומדן**, ו-9 החוזים המסומנים מופיעים בדוח
כדי שאפשר יהיה להזין בהם את הסכום הנקי האמיתי.

## ⚠ למה כתוב כאן ״ספק א׳״ ולא שם

הריפו הזה ציבורי. שם ספק **יחד עם** תמונת ההכנסה השנתית שלו הוא ״נתוני פעילות
פיננסית״ — מידע בעל רגישות מיוחדת לפי תיקון 13 לחוק הגנת הפרטיות. **המספרים
אינם הבעיה; הצירוף לשם הוא.** לכן התיעוד מדבר על ״ספק א׳״. במערכת עצמה, שרצה
מקומית או מאחורי התחברות, השמות מופיעים כרגיל.

⚠ הסרה מ-HEAD **אינה** מסירה מהיסטוריית ה-git. השם עדיין ניתן לאחזור מקומיטים
קודמים; ניקוי מלא דורש כתיבה מחדש של ההיסטוריה, או העברת הריפו לפרטי.

## מה נמצא בגיליון המקור

מלא ב-`seed/discrepancies.md` (נוצר בכל ייבוא) ובלשונית **״ממצאים בגיליון״**.
הכותרות:

1. **אחוז הרווח חושב על ההוצאות ולא על ההכנסה** — `(AA133-AB133)/AB133` הוא
   markup, לא margin. מוצג 15.84%; שיעור הרווח מהמחזור הוא 13.68%.
2. **שורת הסיכום לא מתאזנת** — סכום הקטגוריות 936,750.08 מול סה"כ 940,050.08.
3. **הסיבה: טווחי `SUBTOTAL` קטועים** — `SUBTOTAL(9,Y2:Y118)` בזמן שהנתונים
   מגיעים עד שורה 132. 14 בניינים ו-3,300 ₪ נופלים מהחישוב (וב-`X2:X119` עוד 13).
   בנוסף, ברוזנסקי 25 נוסחת הסה"כ נערכה ביד ומדלגת על עמודות `H` ו-`I`.
4. **ארבע רשימות שלא מסכימות** — 35 פעילים בלי עובד, 25 לא-פעילים שעובד עדיין
   רשום עליהם, `בן גוריון 1` בשתי הרשימות.
5. **כתובות דומות** שלא מוזגו — להכרעת רונן.
6. **מע״מ רעיוני** — ראה למעלה.
7. **2 בניינים בהפסד** (נווה אלון 8-20, אפרים קציר 10) ו-10 מתחת ל-5%.
8. **`'-'` כטקסט** בעמודות מספריות — נספר באקסל כאפס בשקט.
9. **4 עמודות ביקורת תקופתית ריקות ב-131 מתוך 131.**
10. **שורת רפאים 1002** ומבנה עמודות שונה בגיליון "לא פעילים".

### תיקון לממצא שדווח בטעות

בקריאה ראשונה דיווחתי ש**"הנוסחאות נמחקו"** ב-89/126/127 שורות. **זו הייתה טעות
שלי.** אקסל שומר נוסחה חוזרת בצורת `shared` — הטקסט יושב על תא-האב ושאר התאים
מפנים אליו ב-`si` — ולכן הם נראים ריקים לקורא שמפרסר את ה-XML הגולמי בלי לפרש
`si`. **כל השורות וכל סיכומי הקטגוריות מחזיקים נוסחה.** מה שכן שבור זה הטווחים
(ממצא 3), וזה נכשל בשקט. הדוח והמסך אומרים את זה במפורש.

## פרוסה 2 — ביקורות תקופתיות וספקים

### ביקורות: מסך הזנה, לא מסך דיווח

נקודת הפתיחה היא **131 בניינים × 4 סוגים = 524 תאים, אפס מהם מתועדים**. מסך
שרק צובע אותם באדום לא היה משנה כלום — הוא היה הופך את החוסר לרעש שמתרגלים
אליו, בדיוק כמו העמודות הריקות בגיליון. לכן לשונית **״ביקורות״** היא קודם כול
מסך הזנה: סימון מרובה, בחירת סוג ותאריך, ו**תצוגה מקדימה של מה בדיוק ישתנה**
לפני האישור. 131 בניינים נרשמים בלחיצה אחת.

שתי הכרעות שנגזרות מהמצב הזה:

**״מעולם לא תועד״ אינו ״פג תוקף״.** שני מצבים שונים לחלוטין: אחד אומר ״לא
בוצעה או שלא רשמנו״, השני אומר ״בוצעה ועבר זמנה״. ערבובם היה מייצר רשימה של
524 פריטים אדומים שאי אפשר לעבוד איתה.

**חלון ההתראה נגזר מהתדירות ולא קבוע.** 60 יום לפני מועד שנתי הם התראה סבירה;
לפני מועד חצי-שנתי הם שליש מהמחזור. לכן `min(60, interval/4)`.

> ⚠ **התדירויות הן ברירות מחדל, לא קביעה משפטית.** גילוי אש, כיבוי אש וניקוי
> מאגרים — שנתי; גנרטור — חצי-שנתי. ניתנות לעקיפה פר בניין דרך `intervalMonths`.
> אימות מול הדין, מול דרישות המבטח ומול הוראות היצרן הוא שער משפטי (עדי), לא
> החלטה של המערכת.

### ספקים: השאלה שאי אפשר היה לשאול

בגיליון הספק היה **שם בתא**, ליד כל בניין בנפרד. אי אפשר היה לשאול *״כמה אנחנו
משלמים לו בסך הכל״*. עכשיו זו השורה הראשונה בטבלה — ומה שהיא מגלה:

| | |
|---|---|
| **ספק א׳** | **82 בניינים · 342,730 ₪/חודש · 36.5% מכלל ההוצאה** |
| 5 הספקים הגדולים | **48% מההוצאה** |
| ספקים עם הוצאה בפועל | 82 (מתוך 85 רשומים) |
| הוצאה מכוסה בחוזי ספק | 609,073 ₪ מתוך 940,050 ₪ |

ספק בודד שמחזיק **יותר משליש מההוצאה** הוא גם נייר עמדה למשא ומתן וגם ריכוזיות
שכדאי להיות מודעים לה. זה היה בגיליון כל הזמן, מפוזר על פני 82 שורות.

### ״ותק מחיר״ במקום ״מועד חידוש״ — ולמה

היה מתבקש להוסיף שדה ״תאריך חידוש חוזה״ ולבנות עליו התראות. **לא עשינו את זה:**
לגיליון אין מושג כזה, וכל 85 הספקים היו מקבלים שדה ריק — בדיוק התקלה של ארבע
עמודות הביקורת, עמודה שנבנתה ואיש לא מילא.

במקום זה נמדד מה שכן קיים: ל-27 חוזים יש `effectiveFrom` שנגזר מהערות הגיליון.
חוזה שמחירו לא זז מעל 3 שנים הוא מועמד למשא ומתן — **5 חוזים, 18,211 ₪/חודש**,
הוותיק שבהם מ-01.11.2021. וחשוב מזה: **2,680 חוזים תקפים ללא תאריך תחולה ידוע
מדווחים בנפרד ולא נספרים כוותיקים.** חוזה בלי תאריך אינו ״ותיק״ אלא ״לא ידוע״,
וספירתו הייתה הופכת רשימת פעולה של 5 פריטים לרשימה של כמעט הכל.

## פרוסה 3 — מחיר קבוע שאפשר לשנות

ההוצאות כאן הן **חוזים קבועים**, לא חשבוניות חודשיות. מה שהיה חסר זה לא מודל
אלא **נתיב כתיבה**: המודל תמך בהיסטוריית מחירים מהיום הראשון, אבל העריכה עשתה
`update` על אותה רשומה ודרסה את הקודמת. התוצאה: מתוך 2,715 חוזים, **בדיוק אחד**
החזיק היסטוריה. המנוע ידע לקרוא היסטוריה; שום דבר לא כתב אותה.

### שתי פעולות, לא אחת

בכל עריכה בוחרים:

| | מה קורה |
|---|---|
| **תיקון** | הסכום הנוכחי היה שגוי → נדרס במקום. **בלי** שורת היסטוריה. |
| **מחיר חדש מתאריך** | המחיר השתנה → הישן נשמר, החדש נכנס לתוקף מהתאריך שנבחר. |

טעות הקלדה אינה שינוי מחיר. אילו כל עריכה הייתה יוצרת שורה, ההיסטוריה הייתה
מתמלאת בתיקוני הקלדה ומאבדת את הערך שלה; אילו אף אחת לא הייתה — היינו חוזרים
לדריסה. `planPriceChange` מחזירה **תוכנית** ולא מבצעת, והמסך מציג אותה במילים
לפני האישור — שינוי רטרואקטיבי משנה מספרים שכבר דווחו וחייב להיות ניתן לבדיקה.

ארבע מלכודות שהמנוע מכסה, כולן נעולות בבדיקות:
- **תאריך שכבר קיים** → מעדכן את אותה שורה, לא יוצר כפילות.
- **תאריך עתידי** → מותר; הרווח לא זז עד שהתאריך מגיע, והמסך אומר זאת.
- **תאריך בעבר** → מותר עם אזהרה. ״בעבר״ = לפני היום, גם כשהמחיר שהוא מחליף
  הוא ״מאז ומעולם״ ואין לו תאריך להשוות אליו.
- **שורה שלא תשנה את המחיר התקף** (כי קיימת כבר רשומה מאוחרת יותר) → מסומנת
  ככזו, אחרת נראה כאילו העריכה לא עשתה כלום.

### ההכנסה קיבלה את אותו מנגנון — וזה היה החור הגדול

**16 מתוך 24 הערות שינוי-המחיר בגיליון יושבות על עמודה `AA` — דמי הניהול, כלומר
ההכנסה.** ״הסכם ניהול יעלו מ-3550 ל-4200״, ״עלה מ-4600 ל-5400 החל מ-1.11.2021״.
הצד שרונן מתעד הכי הרבה הוא בדיוק הצד שלא היה ניתן לעריכה בכלל.

`managementFee` היה מספר בודד ולכן לא יכול לשאת היסטוריה. נוסף אוסף
**`feeAgreements`** באותה צורה בדיוק כמו חוזה שירות (`amount` + `effectiveFrom`),
ולכן **`activeAsOf` אחד משרת את שני הצדדים** — שני מנועי בחירה היו נפרדים גם
בהתנהגות ברגע שאחד מהם מתוקן והשני לא.

`normalize` ממיר `managementFee` להסכם פותח עם `effectiveFrom: null`, ולכן
`localStorage` קיים ו-seed ישן עולים בלי ייבוא מחדש. ההגירה **אידמפוטנטית**:
הרצה חוזרת לא מכפילה ולא דורסת עריכה.

**3 בניינים** קיבלו היסטוריית הכנסה אמיתית מההערות (גולדין 5, גורדצקי 37,
השיריון 29). הייבוא זורע שורה רק כשההערה נושאת **גם סכומים וגם תאריך**, ורק
כשהסכום ״אחרי״ תואם את התא — אחרת ההכנסה הכוללת הייתה זזה בלי הסבר. הערה בלי
תאריך נשארת הערה גלויה ומדווחת בדוח: שינוי בלי מועד אי אפשר למקם בזמן,
והמצאת תאריך היא המצאת נתון.

### מחיקת שורת היסטוריה

עריכה שיוצרת שורות חייבת לאפשר גם לנקות אותן. `canDeleteEntry` חוסמת דבר אחד:
**את השורה האחרונה** — חוזה חייב להישאר עם מחיר כלשהו.

## בורר ״נכון לתאריך״ — ההיסטוריה הופכת לעדשה

המנועים קיבלו `asOf` מהיום הראשון, אבל התאריך תמיד היה ״היום״ ולכן היסטוריית
המחירים הייתה נראית רק בשורה בודדת. הבורר בראש המסך הופך אותה לעדשה על **התיק
כולו**: מה היו המספרים בתאריך שתבחר.

על הנתונים האמיתיים, מ-01.10.2021 (חודש לפני שדמי הניהול של גורדצקי 37 עלו):

| | היום | 01.10.2021 |
|---|---|---|
| הכנסה | 1,088,983 ₪ | 1,087,933 ₪ |
| הוצאה | 940,050 ₪ | 926,839 ₪ |
| רווח | 148,933 ₪ | **161,094 ₪** |

ובגורדצקי 37 עצמו: דמי הניהול מראים **4,600 ₪** במקום 5,400, בדיוק כפי שההערה
בגיליון אומרת (״הסכם עלה מ-4600 ל-5400 החל מ-1.11.2021״) — ושולי הרווח שלו אז
היו 0.80%. זה מה שההיסטוריה נועדה לענות עליו.

### תאריך עבר = קריאה בלבד

**זו הכרעה, לא מגבלה טכנית.** העורך בוחר את הרשומה התקפה לפי `asOf`; עריכה במצב
היסטורי הייתה משנה את המחיר של יוני בזמן שאתה חושב שאתה מתקן את היום. פעולה
שמצליחה ועושה משהו אחר ממה שנראה היא גרועה מפעולה שנחסמת.

לכן כשהתאריך אינו היום: הפס נצבע, מופיע ״קריאה בלבד״ עם כפתור **חזרה להיום**,
וכל נקודות העריכה — מחיר חוזה, דמי ניהול, רישום ביקורת, רישום מרוכז — נעולות.
המסך **חייב להיראות אחרת**; מספר עבר שנקרא כמספר נוכחי הוא בדיוק סוג הטעות
שהמערכת הזו נבנתה כדי למנוע.

### באג שהבורר חשף

`employeeLoad` מעולם לא קיבל את `feeIndex`, ולכן ההכנסה בטבלת העובדים נגזרה
מ-`building.managementFee` — הערך הסקלרי שהוא **רק זרע הגירה**. כל עוד לא נערכו
דמי ניהול השניים זהים, ולכן זה לא נראה; אחרי העריכה הראשונה הטבלה הייתה מתנתקת
מההסכם התקף. תוקן, ונעול בבדיקה.

## הכל ניתן לעריכה — ומה שאי אפשר, אומר למה

עד עכשיו רק הסכומים היו ניתנים לעריכה: כל שאר השדות הגיעו מהגיליון ונשארו
קפואים. עכשיו כל שדה שרונן מזין בפועל — **עובד אחראי, ספק, כתובת, סטטוס,

וכשעריכה יקרה יותר מקריאה — הנתונים מפסיקים להתעדכן והמערכת חוזרת להיות אקסל.

### שינוי ספק חל על כל שורות המחיר, שינוי סימון רק על התקפה

הבחנה שנראית טכנית ואינה: **ספק** הוא עובדה על הקטגוריה — אם חברת הניקיון
התחלפה, היא התחלפה גם בשורות ההיסטוריה, אחרת ההיסטוריה מייחסת תשלומי עבר לספק

לכל קטגוריה ומתעדכנת מיד עם כל עריכה.

## ענן — צוות אחד, תמונה אחת

עד כה הנתונים ישבו ב-`localStorage` של דפדפן אחד במחשב אחד. **נבדק בפועל:**
אותו מחשב + עותק אחר של הקובץ → אותם נתונים; **מחשב אחר, אותו קובץ בדיוק →
אפס בניינים.** הקובץ הוא התוכנה, לא הנתונים — ולכן שליחה במייל לא פותרת כלום.

השכבה הזו סוגרת את זה: Firestore + התחברות Google. ראה **`DEPLOY.md`** להעלאה.

### ההכרעה: מסמך לכל ישות, לא blob אחד

שתי סיבות, ושתיהן מכריעות. הנתונים שוקלים **1.08MB** והמגבלה למסמך היא 1MB.
וחשוב מזה — שני אנשים שעורכים blob אחד **דורסים זה את זה**: מי שכתב אחרון
מוחק את מה שהשני עשה בשנייה שלפני. שני מסמכים נפרדים פשוט נכתבים.

### הצורה בזיכרון זהה בשני המצבים

`useData` מחזיר `{ buildings: [], contracts: [], … }` ואת אותן פונקציות כתיבה
בין אם המקור הוא localStorage או Firestore. **אף רכיב לא השתנה במיגרציה** —
12 המסכים לא יודעים אם הם בענן.

### ההרשאות: אין תפקידים, אבל יש שער

הכרעת רונן: ״כולם רואים אותו דבר, אין הסתרה לכלום״ — ולכן אין תפקידים ואין
בידול. **אבל** ⚠ ״מחובר ל-Google״ אינו ״מורשה״: לכל אדם בעולם יש חשבון Google.
בלי בדיקת רשימה, `request.auth != null` היה פותח 131 כתובות ו-85 טלפוני ספקים
לכל מי שמצא את הכתובת. הרשימה יושבת ב-`orgs/vitzman.members` ונאכפת ב-rules.

⚠ **חבר לא יכול להסיר את עצמו.** ארגון שנשאר בלי אף מורשה אינו ניתן לתיקון
מהממשק — הכללים חוסמים גם את מי שהסיר את עצמו רגע קודם. נאכף ב-rules, לא רק ב-UI.

### הסרת גישה אינה מחיקת עובד

⚠ שתי רשימות נפרדות: **עובדים** הם מי שאחראי על בניינים; **מורשים** הם מי
שיכול להיכנס. מחיקת עובד **אינה** מסירה את גישתו. ההסרה נעשית ב״ניהול״ →
״גישה למערכת״, ונכנסת לתוקף מיד בלי deploy.

⚠ **תקרה של 3 מורשים, נאכפת ב-rules.** קו משפטי ולא טכני: מאגר בניהול יחיד עם
עד שני בעלי הרשאה נוספים נהנה מהחובות המצומצמות ביותר בתקנות אבטחת מידע.
הרביעי מוציא את המאגר מהקטגוריה ומחייב נוהל אבטחה כתוב, תיעוד גישה, הדרכות
וביקורת אחת ל-24 חודשים.

### שתי חבילות בדיקה חדשות, מול אמולטור אמיתי

⚠ **שתי גרסאות לאותם כללים, ושתיהן נבדקות.** `firestore.rules` נושא הערות
בעברית; `firestore.rules.paste` הוא אותו קובץ עם הערות ASCII בלבד, והוא מה
שמודבק בקונסולה — טקסט דו-כיווני בעורך קוד בדפדפן עלול להישבר, וכלל שלא
מתקמפל הוא מסד חסום. `RULES_FILE=firestore.rules.paste npm run test:rules`
מריץ את אותן 26 הבדיקות על **הטקסט המדויק שמודבק**. אם משנים אחד — לעדכן
את השני ולהריץ את שניהם.

`npm run test:rules` — **26 בדיקות** על `firestore.rules`: שזר מחובר לא קורא
את הספקים, שאנונימי לא קורא כלום, שחבר לא נועל את עצמו החוצה, ושמייל באותיות
גדולות עדיין מזוהה.

⚠ **הבדיקות תפסו באג שהיה חוסם את כולם.** `members()` הוגדרה בשורש, שם
`$(orgId)` אינו קיים — כל `get()` החזיר ״Null value error״, כלומר **דחייה של
רונן עצמו**. בדיקות ה-deny עברו מהסיבה הלא נכונה; רק הבדיקות **החיוביות**
חשפו את זה. בלעדיהן זה היה מגיע לרונן כ״טעינת הנתונים נכשלה״.

`npm run test:cloud` — **20 בדיקות** על שכבת הנתונים מול Firestore אמיתי, עם
כל 3,335 המסמכים ודרך הכללים: שהייבוא נחתך ל-8 מנות ועובר, שהסכומים חוזרים
**לשקל** (1,088,983 / 940,050.08 / 148,932.92), ש-`null` שורד (29 חוזים
״הוועד משלם ישירות״), ששיוך מרוכז הוא `merge` ולא דורס את הכתובת, ושייבוא
חוזר **מחליף ולא מוסיף**.

⚠ שלוש מלכודות שנבדקות רק כאן: מגבלת **500 הפעולות** ל-batch (הייבוא כותב
3,335); **`undefined` מפיל כתיבה שלמה** ב-Firestore בעוד `null` חוקי ומשמעותי
אצלנו; ו**ייבוא חוזר שלא מוחק** היה משאיר לנצח בניין שנמחק מהגיליון.

### הקובץ העצמאי לא נפגע

Firebase מוחלף ב-stub בבנייה העצמאית (`vite.config.js`). בלי זה הקובץ קפץ
מ-631KB ל-**1,173KB** בשביל SDK שלא ירוץ שם לעולם — הוא נפתח מהדיסק בלי
`.env`, ולכן `isFirebaseConfigured` שם הוא תמיד `false`. עכשיו 641KB.

## גיבוי — קרא את זה לפני שאתה מזין נתונים

**כל הנתונים יושבים ב-localStorage של דפדפן אחד.** ניקוי היסטוריית גלישה, מעבר
למחשב אחר או חלון פרטי — וחודשים של הזנה נעלמים **בלי אזהרה ובלי דרך חזרה**.

לשונית **״גיבוי״** סוגרת את זה:

- **שמירת גיבוי** — המצב המלא לקובץ JSON. אפשר לטעון אותו חזרה ולקבל בדיוק
  את מה שהיה. **שמור אחרי כל סבב הזנה.**
- **טעינת גיבוי** — מאמת לפני שדורס, ומראה מה עומד להיטען. שחזור הוא פעולה
  הרסנית, ולכן הוא ניתן לבדיקה מראש.
- **ייצוא CSV** — רווחיות (131 שורות), ביקורות (524), היסטוריית מחירים (2,849).
  אלה **לקריאה ולדוחות בלבד; אי אפשר לשחזר מהם**, והמערכת לא מתחזה שכן.

⚠ לכל קובץ CSV יש **BOM** בראש. בלעדיו אקסל בעברית קורא UTF-8 כ-Windows-1255
ומציג ג׳יבריש — לקח שנצרב ב-project-budget, ובדיקה נועלת אותו כאן.

## מסלול ייבוא אחד לשני הצדדים

לוגיקת הייבוא ישבה בתוך סקריפט שמייבא `node:fs`, ולכן **חייבה התקנת Node רק כדי
להפוך אקסל ל-JSON**. היא חולצה ל-`src/utils/importWorkbook.js` — טהורה, מקבלת
חוברת SheetJS ומחזירה `{ ok, checks, payload, report }`.

אותה פונקציה בדיוק רצה ב-CLI ובדפדפן, ולכן **אין שני מסלולי ייבוא שיכולים
להיפרד**. גם קריאת הקובץ אוחדה: שני הצדדים קוראים `XLSX.read` על בתים.

היא **לא זורקת ולא יוצאת מהתהליך** — מחזירה תוצאה, והקורא מחליט. ייבוא שנכשל
במבחני ההתאמה מחזיר `payload: null`: לא נתונים חלקיים שנראים תקינים.

## עמידות הייבוא — מה קורה כשהקובץ לא בדיוק כמו שציפינו

הייבוא התאים במקור לגרסה אחת של הגיליון והתייחס אליה כאל אמת. שתי תוצאות:

**1. שמות לשוניות הושוו במדויק.** שמות הלשוניות נושאים רווחים לא סדירים
(`"רשימת  בנינים בחלוקה לעובדים "` — רווח כפול ורווח בסוף), וגרסה מעודכנת של
הקובץ הפילה את הייבוא עם `Cannot read properties of undefined (reading '!ref')`
— קריסה שלא אומרת איזה גיליון חסר. עכשיו ההתאמה **סלחנית לרווחים**, ואם הגיליון
הפעיל באמת חסר מתקבלת שגיאה ש**מונה את הגיליונות שכן נמצאו בקובץ**.

**2. שלושת הגיליונות המשניים הם אופציונליים.** רק הגיליון הפעיל הכרחי — כל
הכספים בו. חסר גיליון עובדים? הייבוא ממשיך, כל הבניינים מסומנים ״ללא עובד
אחראי״, והחוסר מדווח. נפילה שלמה בגלל לשונית משנית היא תגובה לא מידתית.

**3. ספירות ספציפיות-לקובץ הפסיקו לחסום.** שלושה מבחנים נעלו את *הגרסה שקיבלתי*
— 131 בניינים, 3 עובדים, 161 הערות. **הוספת בניין אחד הייתה מספיקה כדי לדחות
ייבוא תקין לחלוטין.** הם הופרדו:

| | דוגמה | התנהגות |
|---|---|---|
| **חוסם** — עקביות פנימית | הסכום שחישבנו מול הסכום שהגיליון עצמו מצהיר | כישלון = הייבוא שגוי, שום דבר לא נכתב |
| **לידיעה** — ספירות | 131 בניינים, 3 עובדים | מדווח, לא חוסם |

ההבחנה חשובה: מבחן שנגזר מהקובץ עצמו תקף לכל גרסה שלו; מבחן שנועל מספר קבוע
הוא צילום מצב, ובתור שער כניסה הוא פשוט שגוי.
