# ניהול תקציב פרויקט

מערכת לניהול תקציב, תזרים וחשבוניות בפרויקטי בנייה/שיפוץ שמקבלים החזר מרשות
(מס רכוש / קרן פיצויים). נבנתה סביב פרויקט פינסקר 9 תל אביב, אבל **רב-פרויקטית**.

## הרעיון בשורה אחת

**פנקס חשבוניות אחד, שלושה מבטים.** תזרים, תקציב מול ביצוע, והחזרי הרשות אינם
שלוש טבלאות — הם שלושה חתכים של אותה חשבונית:

```
                     ┌──► תשלומים ──────────► תזרים
חשבונית ─────────────┼──► שיוך לסעיף ───────► תקציב מול ביצוע
                     └──► שיוך למנה ────────► החזרי הרשות
```

## הרצה

```bash
npm install
npm run dev          # http://localhost:5192
```

בלי `.env` האפליקציה רצה **במצב מקומי** — הנתונים ב-localStorage של הדפדפן,
בלי ענן ובלי התחברות. זה מספיק כדי להתחיל להזין חשבוניות אמיתיות היום.

## ייבוא נתוני פינסקר 9

```bash
npm run import:pinsker
```

קורא את שלושת קבצי האקסל מ-`C:/Users/RONEN/Desktop` (או מ-`PINSKER_SRC`) וכותב
`seed/pinsker-9.json`. בסיום מריץ **מבחן התאמה** מול הגיליון — אם מספר לא יוצא
בדיוק, הקובץ לא נכתב. באפליקציה: מסך הפתיחה → "ייבוא מקובץ".

הקובץ מכיל: 91 סעיפי כתב כמויות ב-23 פרקים · 5 שורות עלות · 20 חודשי תזרים ·
27 אירועי מימון · 3 מנות הגשה.

### שלוש החלטות מודל שכדאי להכיר

**1. לחשבונית שני מחזורי חיים, לא אחד.** `status` (טיוטה→מאושרת→שולמה) עונה על
"מה קרה לכסף שלי". `claimStatus` (זכאית→הוגשה→אושרה/קוצצה) עונה על "מה קרה מול
הרשות". הם רצים במקביל — חשבונית יכולה להיות משולמת וטרם מוגשת, או מוגשת ומקוצצת.
איחוד שלהם לשדה אחד הוא בדיוק מה שהופך מעקב החזרים לבלגן.

**2. שלושה בסיסי תקציב, לא אחד.** כתב הכמויות נושא `priceInitial` / `priceSubmitted` /
`priceApproved`. חריגה מול **אושר** = כמה הרשות תחזיר. חריגה מול **ראשוני** = כמה זה
באמת עולה. בפינסקר הרשות קיצצה 2,126,208 ₪ לפני מע״מ — עבודה שתבוצע ותשולם
מהכיס. מדידה מול בסיס אחד מייצרת תמונה שגויה בשני הכיוונים.

**3. הבידוד הוא בנתיב, לא בשדה.** `projects/{id}/<collection>` ולא `ownerId` על כל
שורה. כך שאילתה על תת-אוסף לא זקוקה ל-`where` שהכללים יאמתו — מלכודת שנצרבה
בפרויקט קודם (*כללים אינם מסננים*).

### פרמטר העיכוב בתזרים

`delayDays` הוא עיכוב **מעבר לתוכנית**, לא הפיגור המוחלט. התוכנית כבר מניחה פיגור
מסוים (בפינסקר: הגשה 11/10 → תקבול בנובמבר ≈ 30 יום), ולכן `+30` פירושו "מאחר
בחודש נוסף". החישוב חודשי, כי כך הפרויקט מתנהל בפועל.

## אזהרות

> **המערכת מכינה מנה — היא לא מגישה אותה.** ההגשה לרשות היא הגשה רשמית ונעשית
> ע"י המשתמש. המערכת מסמנת "הוגש" בדיעבד בלבד.

> **`seed/*.json`, `samples/` וקבצי `*.xlsx` מוחרגים ב-`.gitignore`** — הם מכילים
> חשבוניות וסכומים אמיתיים של ספקים אמיתיים. הפרויקט מיועד לריפו **פרטי** נפרד.

> **שער משפטי לפני deploy** — נתוני צד שלישי (ספקים), DPA+ZDR מול Anthropic
> לסריקת AI, ו-DPA של Google. ראה `vault/Meeting Notes/project-budget-app.md`.
