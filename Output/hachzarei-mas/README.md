## הכלל שהכי חשוב לדעת לפני שנוגעים

**כל המקדמים, הספים והטקסטים יושבים ב-`shared/config/`.** אין מקדם קשיח בשום רכיב.

אבל מודל הניקוד הוא **מכפלה** של כל המקדמים, וזה אומר ששינוי מקדם אחד מזיז את
כל ההתפלגות. גרסה 1.0 של האפיון נשברה בדיוק כאן פעמיים:

- מקדם `0.1` נראה כמו "החלשה חזקה", אבל בפועל אף צירוף שכלל אותו לא הגיע לסף
  המדרג הנמוך ביותר — כלומר הוא היה **שער קשיח מוסווה** שפסל 100% מהלידים.
- סף מדרג נקבע ל-`0.9`, שהוא בדיוק `0.75 × 1.2` — הצירוף השכיח ביותר בשאלון.
  ב-IEEE-754 הערך הזה הוא `0.89999999999999991`, ולכן ההכרעה בין שני מדרגים
  עבור הגולש הנפוץ ביותר נקבעה בשגיאת ייצוג בינארית.

**לכן: אחרי כל שינוי מקדם או סף — להריץ את הבדיקות.**

```bash
npm test
```

הן בודקות את ההתפלגות בפועל (`56/25/47` בהחזר מס, `7/7/10` במס שבח), שאין מקדם
שהוא שער בפועל, שכל שער נושא כותרת ונימוק משלו, ושאין סכומי החזר בשום טקסט לגולש.
נפילה שם היא לא "בדיקה שבורה" — היא התפלגות שהשתנתה.

### בדיקות הכללים

`npm test` הרמטי ולא דורש כלום. בדיקות ה-`firestore.rules` דורשות אמולטור פעיל,
ולכן הן סקריפט נפרד. בטרמינל אחד:

```bash
npm run emulate
```

ובשני:

```bash
npm run test:rules
```

13 בדיקות שמוודאות שהלקוח — אנונימי או מחובר — לא קורא ולא כותב ל-`leads`,
ל-`rateLimits` ול-`mail`, ושאין אוסף שנשאר פתוח בטעות. הן רצות מול האמולטור
ומקבלות ממנו `PERMISSION_DENIED` אמיתי — לא בדיקה של הקובץ, בדיקה של ההתנהגות.

## הקמת Firebase

1. פרויקט חדש ב-[console.firebase.google.com](https://console.firebase.google.com).
2. **Firestore → Create database → מיקום `me-west1` (תל אביב).**
   זה לא פרט טכני: המיקום הזה משאיר את נתוני הלידים בישראל ומייתר את גילוי
   ההעברה לחו"ל שמדיניות הפרטיות הייתה חייבת אחרת.
3. `.firebaserc` → להחליף את `REPLACE_WITH_FIREBASE_PROJECT_ID` במזהה הפרויקט.
4. **TTL policy** על אוסף `rateLimits`, שדה `expiresAt` — מנקה את מוני הקצב.
   (`leads` ו-`mail` **לא** צריכים TTL — `purgeExpiredData` מטפלת בהם בקוד, ראה למטה.)
5. **תוסף "Trigger Email from Firestore"** (אוסף `mail`) עם פרטי ה-SMTP של המשרד.
   בלעדיו הליד נשמר אבל לא נשלחת התראה.
6. `cp .env.example .env` ולמלא מזהי GA4 / Meta.
7. למלא את שבעת ה-`{{TODO}}` ב-`shared/config/site.ts`.

## מחיקה אוטומטית — מה שהופך את מדיניות הפרטיות לנכונה

`purgeExpiredData` רצה כל לילה ב-03:15 (שעון ישראל) ומוחקת מ-`leads` ומ-`mail`
כל מסמך שעבר מועד ה-`purgeAfter` שלו. **מחיקה קשה, לא סימון.**

זה לא נוי. עד 22.8.2026 `purgeAfter` רק **נכתב** ואף אחד לא קרא אותו, בזמן ש-`privacy.html`
§4 הצהיר "המחיקה מתבצעת אוטומטית במועד זה". השער המשפטי של עדי תפס את זה כחוסם.
אם מסירים את הפונקציה — **חייבים** לשנות גם את המדיניות.

- לידים: 730 יום (`site.leadRetentionDays`)
- מסמכי `mail`: 30 יום (`site.mailRetentionDays`) — הם עותק שני מלא של הליד,
  כולל תשובות בעלות רגישות מיוחדת, ולכן תור מסירה ולא ארכיון

הלוגיקה מיוצאת בנפרד כ-`purgeExpired()` כדי שאפשר יהיה לבדוק אותה מול האמולטור:
פונקציה מתוזמנת דורשת אמולטור pubsub ואי אפשר לקרוא לה ישירות.

## מה **אסור** לשנות בלי לחשוב פעמיים

| | למה |
|---|---|
| `exposeScoreToVisitor: false` | הגולש לא רואה ציון, אחוז או סכום בשום מסך |
| סכומי החזר בטקסט | §9.2 — הצגת סכום לפני בדיקת מסמכים חושפת לטענת הטעיה. יש בדיקה שאוכפת |
| `required: false` על `consent` | §9.3 — התניית קבלת התוצאה בהסכמה שיווקית היא התניית שירות בהסכמה |
| `assertComplete` בשרת | בלעדיה אפשר לקנות מדרג A בהשמטת שאלות |
| `resolveTier` על ציון גולמי | עיגול לפני ההשוואה הזיז מדרג שלם |
| ערך ההמרה מה-tier של **השרת** | אחרת החישוב מחדש בשרת חסר משמעות בפיקסל |
| `firestore.rules` | הלקוח לא קורא ולא כותב לידים. אף פעם |
| `purgeExpiredData` | היא מה שהופך את הצהרת המחיקה ב-`privacy.html` §4 לנכונה |
| `purgeAfter` על מסמכי `mail` | בלעדיו הליד המלא נשאר לנצח גם אחרי שהליד עצמו נמחק |
| נוסח מדרגי התוצאה | יש בדיקה שאוסרת "סבירות גבוהה", "מגיע לך", "אתה זכאי" בטקסט המדרגים |
| `ctaType` שאינו `'none'` | כל מדרג חייב מסלול פנייה — אחרת שורת האמון משקרת |
| גילוי שכר הטרחה | חייב להיות גלוי במסך התוצאה, לא רק ב-FAQ המקופל |
