# מערכת ניהול לידים — החזרי מס שבח

שכבת הנתונים של דף הנחיתה: קליטת לידים, אחסון, בקרת גישה, מחיקה אוטומטית,
וקונסולה למשה. דף הנחיתה עצמו נבנה בנפרד (עומר) וטוען מכאן קובץ אחד:
`lead-intake.js`.

**סטאק:** Vite + React 18 + Tailwind v3 + Firebase (Firestore / Auth / Functions
/ Hosting), JavaScript.

מתוך סקירת ה-privacy-by-design של עדי (`adi/Outputs/2026-08-15-mas-shevach-privacy-by-design.md`),

המסקנה המבנית: **כל התקציב ההגנתי יושב בבקרת גישה, מחיקה ואבטחה — לא בסכימה.**

## סכימת `leads`

### שדות היצירה — נעולים (עדי S3)

| שדה | טיפוס | הערה |
|---|---|---|
| `firstName` | string, 2–40 | שם פרטי בלבד. **אין שם משפחה.** ללא ספרות |
| `phone` | string | `^0[2-9]\d{7,8}$` |
| `email` | string ≤100 | **אופציונלי** |
| `screened` | bool | 🔴 **בוליאני יחיד.** לא ארבע תשובות הבודק |
| `source` | map | ייחוס שיווקי: `utmSource/utmMedium/utmCampaign/utmContent` **בלבד** |
| `policyVersion` | string ≤32 | 🔴 **ראיית ההסכמה. שדה עליון** — ראה למטה |
| `createdAt` | timestamp | `== request.time`. הקליינט אינו שולט בו |

#### 🔴 M4 — אין הסכמת דיוור במערכת

תיבת ה-opt-in **ירדה לגמרי** בשער של עדי: השדה, אוסף `marketingSubscribers`,
והענף ב-`onLeadCreated`. שלושה כשלים מצטברים, לא ניסוח:

- התיבה הבטיחה **מסרונים** בזמן שנשמר **אימייל בלבד**;
- האימייל אופציונלי, ולכן הסכמות נפלו בשקט — opt-in לדיוור בלי כתובת לדוור אליה;
- **לא היה מנגנון הסרה בקוד כלל**, וס' 30א מחייב אותו בכל הודעה.

> **עדיף לא לאסוף מאשר לאסוף חלקית.** הסכמה שנשמרת ואי אפשר לממש אותה או לחזור
> ממנה גרועה מאי-איסוף, כי היא יוצרת **מצג של הסכמה**.

`marketingOptIn` (ועוד 6 שמות קרובים) נמצאים ב-`FORBIDDEN_FIELDS` — כלומר
החזרת התיבה מחייבת מעבר דרך עדי, לא עריכה של שורה אחת. יש 4 אסרשני rules
ו-2 אסרשני wire שמוודאים שהשדה נדחה גם ב-POST ישיר, ושאוסף הדיוור נפל תחת
ה-deny-by-default הסוגר.

**➜ כשיהיה דיוור אמיתי:** אוסף נפרד · ערוץ מוצהר שתואם למה שנאסף · מנגנון
הסרה בכל הודעה · תיעוד הסכמה. סבב חדש אצל עדי.

#### למה `policyVersion` הוא שדה עליון ולא בתוך `source`

`source` הוא **ייחוס שיווקי**; `policyVersion` הוא **ראיה להסכמה**. לשניים
מחזורי חיים שונים לחלוטין — וג'וב עתידי שינקה ייחוס שיווקי אחרי N חודשים (דבר
סביר לגמרי לעשות) היה **מוחק בשקט את ראיית ההסכמה יחד איתו**.

✅ **אין `optInAt` נפרד**: הטופס נשלח פעם אחת, ולכן `createdAt` — שהוא זמן שרת
ולא נשלט ע"י הקליינט — הוא גם מועד ההסכמה.

#### 🔴 `POLICY_VERSION` נבדק מול המדיניות שפורסמה

`POLICY_VERSION = "1.0"` ב-`src/constants.js` **חייב להופיע כגרסה בתוקף** ב-
`Output/2026-08-15-mas-shevach/privacy.html`. `npm run check` (סעיף F) נכשל אחרת.

שתי מחרוזות שמתוחזקות בנפרד מתפצלות בעריכה הראשונה, ומאותו רגע כל ליד נושא
ראיית הסכמה שמצביעה לשום מקום — **בלי ששום דבר ייראה שבור**. זה בדיוק הדפוס של
M5. שלושת מצבי הכשל נבדקו: דריפט גרסה · הגרסה קיימת רק כשורה היסטורית · המדיניות
חסרה.

הבדיקה קוראת קובץ מחוץ לפרויקט. נתיב חלופי:
`npm run check -- --privacy <path>`. קובץ חסר = חוסם go-live (לא כשל build),
כדי שהפרויקט יישאר בר-בנייה גם בלי דף הנחיתה לצדו.

> ⚠️ הגרסה נגזרת מ**הטקסט שהוצג בפועל**, לא ממעמד האישור המשפטי — ולכן היא
> `1.0` ולא `1.0-draft` אף שהמסמך עדיין מצריך בדיקת עו"ד. אם עו"ד ישנה נוסח
> לפני go-live: מעלים ל-`1.1` בשני המקומות, ואין נזק כי עדיין אין לידים.

### אסור מבנית — לא "לא כרגע", אלא לא

ת.ז. · סכומים (שווי, מס ששולם, החזר צפוי) · תאריך מכירה · כתובת נכס · גוש/חלקה ·
מספר שומה · שם משפחה · **שדה טקסט חופשי** · **ארבע תשובות הבודק כערכים נפרדים**.

**וגם — הדפוס, לא רק המופע:** טקסט או מזהה שמקורו **במשתמש או בפלטפורמה**,
שנכנס דרך שכבת האנליטיקס ועוקף את S3 **בדלת צדדית** — בלי ששום שדה טופס נפתח:

| נחסם | למה |
|---|---|
| `utm_term` | מילת החיפוש שהמשתמש **הקליד**. כאן: "מכרתי דירה ושילמתי 240 אלף מס" |
| `document.referrer` המלא | נושא את שאילתת מנוע החיפוש המפנה |
| URL הנחיתה המלא / query string | אותו דבר |
| `gclid` / `fbclid` / `msclkid` | מזהי קליק שמקשרים את הליד לפרופיל שלו אצל Google/Meta. הצידוק היחיד להחזיק בהם — ייבוא המרות אופליין — **כבר נחסם ב-S11(1)**. כלומר סיכון קישור **בלי שום שימוש מותר**, ומה שאין לו שימוש מותר לא נאסף |
| ✅ `utm_source/medium/campaign/content` | **נשארים** — אנחנו קובעים אותם, לא המשתמש |

`document.referrer` ו-`location.href` **אינם מופיעים בקוד הקליינט בכלל**, ויש על
כך אסרשן ב-`npm run check` (סעיף E2).

הרשימה המלאה: `FORBIDDEN_FIELDS` ב-`src/constants.js`. היא נאכפת ב-`hasOnly`
ב-rules (ההגנה האמיתית), בסינון ב-`lead-intake.js`, וב-`npm run check`.

**למה לא ארבע התשובות:** `soldProperty + within6y + employmentStatus + taxPaid`
יחד **הם תיק מס מזערי**. `screened: true` נושא את כל הערך התפעולי בלי אף אחד
מהסיכונים.

## בקרת גישה

```
leads/{id}       create: ולידציה מלאה (כל אחד — זו נקודת הכתיבה הציבורית)
                 get,list: בעלים בלבד
                 update,delete: if false   ← 🔴 גם למשה
suppression/{h}  שרת בלבד. אף אחד לא קורא, אף אחד לא כותב מהקליינט
opsLog/{id}      בעלים קורא; שרת בלבד כותב
{document=**}    read,write: if false      ← deny-by-default
```

**"מחובר" אינו "מורשה" (R-4).** כל בעל חשבון Google בעולם הוא
`request.auth != null`; במאגר הזה זה אומר שכולם קוראים את רשימת הלידים. הבעלות
נקבעת בשני מסלולים מפורשים: custom claim `role == 'owner'`, או allowlist מיילים
ב-`ownerEmails()` בתוך `firestore.rules` (עם `email_verified`).

**למה `update, delete: if false` גם למשה:** דפדפן שנפרץ או session גנוב לא יכולים
למחוק את המאגר, לדרוס נתונים או לזייף סטטוס — הם יכולים רק לקרוא. כל מוטציה עוברת
ב-callable שרצה ב-Admin SDK, מוגבלת-שדות ומתועדת ב-`opsLog`.

## מדיניות שמירה ומחיקה (עדי S8) — מנגנון, לא הערה

| מצב | תקופה | מאיפה נמדד |
|---|---|---|
| ליד שלא נענה | **6 חודשים** | מיצירת הליד |
| נוצר קשר ולא התקדם | **12 חודשים** | מהמגע האחרון |
| סירב מפורשות | **מיידי** | + רשומת דיכוי מינימלית |
| הומר ללקוח | **מיידי** | יוצא מ-`leads` למערכת התיקים |

**המימוש:** `purgeExpiredLeads` — Cloud Function מתוזמנת, כל יום ב-03:00
(Asia/Jerusalem). הלוגיקה עצמה ב-`src/utils/retention.js`, **מיובאת גם ע"י
הקונסולה וגם ע"י ה-Function** — ולכן "נמחק בעוד X ימים" שהמסך מציג הוא בדיוק מה
שהשרת מבצע. יש גם `purgeExpiredLeadsNow` (callable, בעלים) כדי **להוכיח** שהמנגנון
עובד ביום ההקמה במקום לחכות 6 חודשים ולגלות שלא.

> "מדיניות שאומרת 12 חודשים ומאגר שמכיל לידים מ-2026 היא **הצהרה כוזבת** על
> אמצעי הגנה" — עדי S8(3).

**ההבחנה בעוגן אינה קוסמטית:** "לא נענה" נמדד מ*יצירת* הליד, "נוצר קשר" מ*המגע
האחרון*. אילו שניהם נמדדו מהמגע האחרון, כל שיחה נכשלת הייתה מאריכה את חיי הליד —
כלומר מי שלא עונה היה נשמר הכי הרבה זמן. יש על כך אסרשן ב-smoke.

### רשומת הדיכוי — HMAC, ושלושת התנאים של עדי

מזהה המסמך הוא **HMAC-SHA256 של הטלפון**; הטלפון עצמו אינו נשמר. רשימת טלפונים
של מי שפנה לשירות החזרי מס שבח היא בעצמה המידע הרגיש.

**🔴 1. איפה מתבצעת הבדיקה: בצד שרת בלבד. אין לזה נתיב קליינט.**

זו הנקודה שקובעת אם ה-HMAC שווה משהו: גיבוב של טלפון ישראלי בלי מפתח סודי הוא
~10⁸ אפשרויות — נפרץ בשניות. **אם המפתח מגיע לדפדפן, ההגנה מתאפסת.**

| | |
|---|---|
| `hashPhone()` | `functions/src/common.js` בלבד |
| המפתח | `process.env.SUPPRESSION_SECRET` — Firebase Secret, לא `VITE_*` |
| קוראים | `onLeadCreated` · `setLeadStatus` — Cloud Functions בלבד |
| הקליינט | **לא מגבב, לא קורא, לא כותב.** ב-rules: `suppression` = `if false` לכולם, כולל הבעלים |

הבדיקה "האם מספר זה סירב" רצה ב-`onLeadCreated` — כלומר **אחרי** שהליד נכתב,
בשרת. לכן הקליינט לא צריך (ולא יכול) לדעת דבר על הרשימה.

**זה נאכף כאסרשן, לא כהבטחה:** `npm run check` סעיף E1 נכשל אם המחרוזות
`SUPPRESSION_SECRET` / `hashPhone` / `createHmac` מופיעות ב-`src/` או ב-`intake/`,
ו-E-נוסף מוודא ש-`suppression` חסום מוחלט ב-rules.

**🔴 2. יציבות המפתח — חשיפה לפי ס' 30א, לא נוחות.**

רוטציה או אובדן של `SUPPRESSION_SECRET` **מנתקים את כל רשומות הדיכוי הקיימות
בלי שחזור** — הגיבובים הישנים לא יתאימו יותר. התוצאה בפועל: **מי שביקש להסיר
אותו יקבל שוב פנייה**, וזו הפרה של בקשת הסרה.

- ❌ **לא לבצע רוטציה** למפתח הזה כחלק מ"היגיינת סודות" תקופתית.
- ✅ לגבות אותו **מחוץ ל-Firebase** (מנהל סיסמאות של המשרד), עם תיעוד מה הוא עושה.
- ⚠️ אם חייבים להחליף אותו: זו **הגירה**, לא החלפת ערך. אין דרך לחשב מחדש
  את הגיבובים בלי הטלפונים המקוריים — שכבר נמחקו. כלומר החלפה = איבוד הרשימה.
  לתעד את ההחלטה לפני שמבצעים.

**🟠 3. זו pseudonymization, לא אנונימיזציה.**

חשוב לניסוח מדיניות הפרטיות: רשומה שניתן לשחזר ממנה זיהוי בעזרת מפתח היא
**מידע מזוהה-למחצה ועדיין מידע אישי**, לא מידע אנונימי. מי שמחזיק גם את המפתח
וגם מספר טלפון יכול לבדוק התאמה. **אין לתאר את זה במדיניות כ"אנונימי".**

**אין ייצוא.** אין כפתור CSV/Excel בקונסולה, ולא בטעות (R-9). רשימה שיצאה מהמערכת
אינה מוגנת עוד בכללים שלה, ומחיקה שאינה כוללת אותה אינה מחיקה.

## הקמת Firebase

1. **פרויקט חדש ומבודד** ב-Firebase Console — לא משותף עם מערכת אחרת של המשרד
   (פריט 10 ברשימת עדי למשה). Firestore ב-**production mode**, region
   `europe-west1`.
2. **Authentication → Google** (ספק יחיד). 🔴 **לא להפעיל Anonymous.**
3. **Web app** → העתקת ה-config ל-`.env` (מ-`.env.example`).
4. **App Check** → reCAPTCHA v3 → `VITE_APPCHECK_SITE_KEY` ב-`.env`.
   🔴 **ואז Console → App Check → Firestore → Enforce.** האכיפה מוגדרת בקונסולה,
   **לא ב-rules ולא בקוד** — זה פריט DoD שעדי מאמתת בצילום מסך.
5. **`ownerEmails()` ב-`firestore.rules`** — להחליף את ה-placeholder במייל של משה.
6. **`.firebaserc`** — מזהה הפרויקט.
7. **סודות ה-Functions:**
   ```
   firebase functions:secrets:set SUPPRESSION_SECRET
   ```
   ⚠️ הסוד חייב להיות יציב. שינוי שלו מנתק את כל רשומות הדיכוי — כלומר מי שסירב
   יקבל שוב שיחה. וכן `OWNER_EMAILS` כמשתנה סביבה ל-Functions.
8. `.env` **לעולם לא ב-git**. מפתחות ה-Web ציבוריים ממילא — ההגנה היא ה-rules.

## מה **לא** נבדק כאן, ואסור להציג כאילו כן

- **App Check מקצה לקצה** — אין לו אמולטור. נתיב ה-reCAPTCHA וההחלפה
  (`exchangeRecaptchaV3Token`) נכתב לפי ה-REST API המתועד, אבל **הורץ רק מול
  אמולטור עם `requireAppCheck: false`**. אימות אמיתי = `selfTest()` מול הפרויקט,

  (`src/utils/retention.js`) ב-smoke, אך **לא הורצו** מול אמולטור Functions.

- **אף ליד אמיתי לא הוזן.** כל הבדיקות מול אמולטור מקומי עם נתונים מומצאים.

## חריגות מהמפרט של עדי — **נסקרו ונסגרו** (סבב 2)

| # | החריגה | הכרעה |
|---|---|---|
| 1 | `policyVersion` | 🟠 **הכוונה אושרה, המיקום תוקן.** תפס אי-עקביות אמיתית (S9 דרש חותמת ומעולם לא נוסף ל-R-2) — אבל לא לקבור אותו ב-`source`. **הועלה לרמה עליונה** + נוסף ל-`hasOnly`. אין צורך ב-`optInAt` נפרד |
| 2 | `firstName` בלי ספרות | ✅ **אושר** — פסילת ספרות ולא allowlist תווים. ראה למטה |
| 3 | HMAC לרשומת דיכוי | ✅ **אושר בשלושה תנאים** — כולם מיושמים ומתועדים למעלה |
| 4 | `utm_term` | ✅✅ **אושר, והדפוס הורחב** ל-`referrer` / URL מלא / `gclid` / `fbclid` |

### ⚠️ תיקון שנדרש בעקבות סבב 2 — באג שהיה בקוד

עדי אישרה את סעיף 2 בנימוק ש**allowlist היה דוחה שמות לגיטימיים, ושם תקין
שנדחה = ליד אבוד**. הנימוק נכון — אבל מה שהיה בקוד היה **בדיוק allowlist**
(`^[A-Za-zÀ-ɏא-ת…]`), לא denylist. הרצה על שמות אמיתיים:

```
עובר  דנה · Daniel · בת-אל · Zoë · José
נדחה  محمد · سارة · Дмитрий
```

כלומר הגרסה הקודמת חסמה בשקט חלק ניכר מהאוכלוסייה בישראל — ליד אבוד בכל מקרה,
וגם הפליה בתוצאה. **תוקן ל-denylist של ספרות בלבד** (כולל ספרות ערביות-הודיות
`٠-٩` ומורחבות `۰-۹`, אחרת ת.ז. נכתבת בהן ועוברת). המטרה המקורית נשמרת במלואה:
בלי ספרות אי אפשר להסתיר ת.ז. יש רשימת רגרסיה קבועה ב-`smoke` וב-`rules-tests`
עם עשרה שמות לגיטימיים, כדי שזה לא יחזור.
