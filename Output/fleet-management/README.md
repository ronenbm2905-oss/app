## מסך 6 — ייבוא מהאקסל

`ייבוא` בסרגל העליון. **בחירת קובץ → תצוגה מקדימה מלאה → אישור.** אין מסלול
שעוקף את התצוגה המקדימה; המשתמש רואה לפני השמירה מה ייווצר, מה סומן לבדיקה
ולמה, ואילו ערכים נדחו — כולל הערך המקורי מהקובץ.

**הפרסור כולו client-side** — הקובץ לא נשלח לשום שרת.

### כללי הניקוי המיושמים (`utils/importExcel.js`, טהור)

| מה | איך |
|---|---|
| מיפוי עמודות | לפי **תוויות** הכותרת, לא לפי מיקום — עמודה שנוספה לא שוברת ייבוא |
| שורות נתונים | רק שורות עם מספר סידורי **וגם** לוחית. שורות זבל מדווחות ולא מיובאות |
| שורת אנשי קשר של הספק | מזוהה לפי מייל/טלפון, **לא** מיובאת כרכב — אבל מזינה את `LeaseCompany` |
| תאריכים | serial של אקסל (epoch 1899-12-30), אובייקט `Date`, או `"D.M.YY"` — שלושתם |
| עלות חודשית | מתקבלת רק כמספר בטווח ₪500–₪10,000. טלפון / serial-תאריך / מחוץ לטווח → **נדחה ומדווח**, לא מנוחש |
| חברת ליסינג | נרמול (רווחים + כתיב מלא/חסר) → רשומה אחת. הווריאנטים המקוריים מוצגים |
| לוחית | נשמרת **raw כמחרוזת** — בלי עיצוב מחדש ובלי המרה למספר (אובדן אפסים מובילים) |
| שם נהג | היוריסטיקה: ספרות / מילת-הקשר / >3 מילים / סוגריים → **טקסט חופשי** |
| הרצה חוזרת | התאמה לפי לוחית (מנורמלת) — רכב קיים מדולג, בלי כפילויות |

### שני כללים שאינם "איכות נתונים" אלא החלטות

**1. טקסט חופשי בעמודת "שם נהג" (D-Import, עדי).** יומן חילופים והערות על
עובדים אינם שם. שורה כזו:

- **לא** יוצרת נהג בשם הזה במאגר;
- הטקסט המקורי נשמר ב-`Assignment.importRaw` — שדה **מבודד**, מסומן "לבדיקה",
  ולעולם לא ב-`notes` התפעולי;
- `Assignment.needsReview = true` → **חוסם שיוך קנס אוטומטי** על בסיס ההחזקה
  הזו, עד שאדמין יאמת מי נהג בפועל.

**2. `fromDateInferred` — תאריך תחילת החזקה משוער.** לאקסל אין תאריך תחילת
*החזקה*, רק תאריך תחילת *הסכם הליסינג*. ההחלטה: משתמשים בו (אחרת השיוך
האוטומטי משותק לנצח), אבל מסמנים. הדגל זורם מ-`Assignment` →
`resolveDriverForFine` → `Fine.attribution.fromDateInferred`, ו**טופס הקנס
מציג אזהרה מפורשת** כשקנס משויך על בסיס תאריך כזה. החזקה שנוצרת ביד = `false`.

### מה **לא** מיובא

גיליון `החזרות רכבים` מוחרג לחלוטין (`EXCLUDED_SHEETS`) — לא מיובא וגם לא
מוצע כברירת מחדל. 79 שורות היסטוריה של עובדים שרובם עזבו = כשל **מזעור**,
לא רק בעיית איכות נתונים.

### ספריית הפרסור

`read-excel-file` (npm, מתוחזק, ESM). **לא** SheetJS/`xlsx` — הם הפסיקו לפרסם
ל-npm, והגרסה שיושבת שם (0.18.5, 2022) נטושה עם advisories פתוחות. שיקולים:

- שומרת על **מספרי שורה אמיתיים** (`rows[i]` ⇔ שורה `i+1`) כולל שורות ריקות —
  קריטי, כי בקובץ הזה הנתונים מתחילים בשורה 4 ושורה 40 היא אנשי קשר;
- אותה חבילה עובדת גם ב-node (`read-excel-file/node`), ולכן אפשר להריץ את
  **אותו פרסור בדיוק** מול הקובץ האמיתי בלי דפדפן;
- המסך נטען lazy (`React.lazy`) — מנוע הפרסור יושב ב-chunk נפרד של ~66KB
  ולא ב-bundle הראשי.

### אימות מול קובץ אמיתי

```bash
npm run import:check -- "C:\path\to\רכבים 20.7.2026.xlsx"          # שמות מצונזרים
npm run import:check -- "C:\path\to\file.xlsx" "20.7.26" --names   # מלא, מקומי בלבד
npm run render:check -- "C:\path\to\file.xlsx"                     # רינדור המסך על הקובץ
```

> ⚠️ **לפני ייבוא 36 העובדים האמיתיים:** סעיף 5.5 בסקירת עדי — הודעת הפרטיות
> צריכה להימסר לנהגים **לפני** שהמערכת מתחילה לרשום עליהם קנסות. המסך דורש
> אישור מפורש של האדמין על כך לפני הכתיבה.

## מסך 7 — תיקון ההחזקות שסומנו לבדיקה

הייבוא מסמן 9 מתוך 36 ההחזקות ב-`needsReview=true`, כי בעמודת "שם נהג" היה
יומן חילופים ולא שם. **אלה היחידות שחוסמות שיוך קנס אוטומטי** — עד שהן
נפתרות, הפיצ'ר המרכזי לא עובד על הרכבים שלהן. המסך (`nav → אימות החזקות`,
מוצג רק כשיש מה לאמת) מרכז אותן, עם מונה "נפתרו X מתוך Y" והתראה מקבילה
בדשבורד שנעלמת כשכולן נפתרו.

לכל פריט שלושה בלוקים מופרדים ויזואלית, וזה כל הרעיון:

| בלוק | מה בו |
|---|---|
| 🟡 צהוב | **מה כתוב באקסל** — `importRaw` כלשונו + הסיבות שבגללן סומן |
| 🔵 כחול | **מה המערכת מנחשת** — הצעה לשם, לתאריך, למחזיק קודם, לרכב מאגר |
| ⬜ לבן | **מה האדמין קובע** — הטופס שנשמר |

### 1. הצעות — לא החלטות

`utils/reviewParse.js` (טהור) קורא את הטקסט החופשי ומפיק הצעה: תאריך בשלושת
הפורמטים שמופיעים בקובץ (`28.4.2026` / `6.5.26` / `17/6/26`, כולל ולידציה
אמיתית — `31.4` נדחה), שם לפי מילת-הקשר (`אצל` / `עבור` / `לעובד`) או לפי
מיקום, ומחזיק קודם לפי המילה `לשעבר`. כל הצעה מציגה **מאיפה נגזרה** ורמת
ביטחון, ו**שום הצעה לא מוחלת מעצמה** — היא נכנסת לטופס רק בלחיצה על "מילוי".
הטרנספורמציות של הלחיצה עצמן טהורות (`utils/review.js → applyNameSuggestion`
וחברותיה) ומכוסות בבדיקות, כדי שההתנהגות לא תהיה חבויה בתוך `onClick`.

### 2. פיצול לשתי החזקות — הערך האמיתי של המסך

שורה כמו `<שם> החל מ 11.1.2026 (<שם> לשעבר)` מתעדת **שני מחזיקים**, וזה בדיוק
המידע שהאקסל איבד: הוא שומר רק את האחרון. בלי פיצול, קנס מ-2025 על הרכב הזה
היה נשלח לנהג הלא נכון. הפיצול יוצר שתי החזקות **רציפות ובלי חפיפה** —
הקודם `[origFrom .. newFrom-1]`, הנוכחי `[newFrom .. ]` — ומאומת בבדיקות
(`prevDay(current.fromDate) === previous.toDate`, `rangesOverlap` שלילי,
ושיוך קנס לפני/אחרי החילופים מחזיר שני נהגים שונים).

### 3. כללי הכתיבה

- אחרי פתרון: `needsReview=false`, `driverId`+`driverUid` מוגדרים.
- **`fromDateInferred` יורד ל-false רק אם הוזן תאריך אמיתי.** נשאר התאריך
  המשוער (תחילת הסכם הליסינג) → הדגל נשאר `true` והאזהרה בטופס הקנס נשארת.
- **`importRaw` נשאר בשדה המבודד גם אחרי הפתרון** — עקבות ביקורת (D-Import של
  עדי). הוא **לעולם** לא מועתק ל-`notes`; בדיקה אוכפת את זה.
- "רכב מאגר / ללא מחזיק קבוע" — פתרון בלי להמציא נהג: הרכב עובר ל-`status=pool`,
  ההחזקה נשארת בלי `driverId`, ושיוך קנס נופל למסלול `pool` המפורש.
- נהג חדש נוצר inline; שם שכבר קיים משויך לרשומה הקיימת ולא מכפיל.
- עקבות: `reviewResolvedAt` / `reviewResolvedBy` / `reviewResolution`, ו-
  `reviewSplitFrom` על ההחזקה ההיסטורית (כדי שהמונה לא יספור אותה כפריט נוסף).

```bash
npm run review:check    # מרנדר את המסך באמת (he+en) ובודק מה מוצג
```

## הלוגיקה שמצדיקה את המערכת

**שיוך קנס לנהג נגזר אוטומטית** מה-`Assignment` שהיה תקף בתאריך העבירה —
לא נבחר ידנית מרשימה. זו הישות שמחליפה את עמודת "שם נהג" שהייתה באקסל יומן
חילופים בטקסט חופשי. הפונקציה הטהורה: `utils/assignments.js → resolveDriverForFine`.

מקרי הקצה מטופלים במפורש ומכוסים בבדיקות:

| מצב | התנהגות |
|---|---|
| החזקה יחידה מכסה את התאריך | שיוך ודאי (`resolved`) |
| החלפה באותו יום / חפיפה | `ambiguous` — נבחר הנהג **הנכנס**, והממשק דורש אישור מודע |
| רכב מאגר בלי החזקה | `pool` — אין שיוך אוטומטי |
| אין החזקה בתאריך | `none` — אין למי לשייך |
| ההחזקה מסומנת "דורש בדיקה ידנית" | `needsReview` — **אין שיוך אוטומטי** (מקורה בטקסט מיובא) |

**עקיפה ידנית** אפשרית, אבל מחייבת נימוק ונרשמת בשרשרת ראיות מלאה
(`Fine.attribution`): מאיזו החזקה נגזר, מתי, מי עקף, למה, ומה היה השיוך הקודם.

**חריגת ק"מ** (`utils/odometer.js → kmStatus`): מכסה יחסית מתחילת החוזה
(`annualKmAllowance × ימים/365`) מול הקריאה האחרונה, פלוס extrapolation
לתחזית בסוף החוזה.

## פרוסה 2 — פורטל הנהג

עובד נכנס עם החשבון שלו, רואה את **הרכב שלו** ומדווח **ק"מ**. זה הכל, וזה
מכוון: כשהאישור הוא חשבון גימייל פרטי שהחברה לא הנפיקה ולא יכולה לכבות,
**רדיוס הפגיעה המינימלי הוא הבקרה שמחליפה את השליטה בחשבון**
(עדי, `adi/Outputs/2026-08-17-fleet-driver-portal-guidance.md`, ס' 3.2.5).

### איך עובד הקישור

1. האדמין ממלא **מייל** בכרטיס הנהג. המערכת **אינה שולחת מייל** — מישהו שולח
   לעובד את הקישור לאפליקציה בדרך הרגילה.
2. העובד נכנס. הקליינט מחפש רשומת נהג עם `userId == uid`; אם אין — רשומה
   **לא מקושרת** שהמייל שלה תואם, ותובע אותה: `userId = uid`,
   `portalStatus = 'active'`.
3. מכאן והלאה **המייל אינו משתתף בשום החלטת הרשאה.** דרישת F1 של עדי: הבידוד
   לפי `uid` בלבד.

**`ניתוק קישור` בכרטיס הנהג הוא אמצעי הביטול היחיד שקיים.** אי אפשר לכבות
חשבון גימייל שהחברה לא הנפיקה; אפשר רק לחסום אותו כאן. הניתוק צורב
`portalStatus = 'revoked'`, שאינו ניתן לתביעה מחדש — אחרת עובד שעזב היה מקשר
את עצמו בחזרה בלחיצה. החזרה דורשת "אפשר קישור מחדש" מפורש.

> **אין שום הנחה על Google.** הקישור נשען על `token.email` +
> `token.email_verified`, שני שדות שקיימים **זהים בכל ספק** ב-Firebase Auth.
> לפרומול אין חשבונות Google ארגוניים (`hildav@promall.co.il` נדחה בפועל;
> הכניסה בוצעה מ-Gmail פרטי), החברה על Microsoft 365 וה-IT חיצוני. מעבר לספק
> Microsoft בעתיד = הפעלה בקונסולה + ניתוק/חיבור מחדש של הנהגים (uid חדש
> לכולם), **ולא שינוי קוד**. לכן כפתור הניתוק אינו רק "לעובד שעוזב" — הוא
> כלי ההגירה.

### `driverPortal` — למה יש אוסף חדש

ב-firestore.rules **אין שאילתות**, ולכן "האם המשתמש הזה מחזיק את הרכב הזה
**היום**" אינה שאלה שאפשר לשאול על מסמך הרכב. שלוש האפשרויות היו: לפתוח לנהג
את כל אוסף הרכבים (36 רכבים — נפסל); לדנרמל `currentDriverId` על הרכב (עובד,
אבל משאיר את הנהג קורא את **מסמך הרכב**, כך שכל שדה שיתווסף לו בעתיד ידלוף
בשקט — זו צורת הכשל של D1); או **ההיטל כמסמך משלו**. נבחרה השלישית:

```
orgs/{orgId}/driverPortal/{driverId}   ← id === driverId, ולכן ההרשאה היא
                                          בדיקה אחת בנתיב ידוע, בלי join
```

המסמך מכיל **רק** את מה שהנהג רשאי לראות: לוחית, דגם, יצרן, שנתון, סיום חוזה,
ופרטי חברת הליסינג. **אין בו `monthlyCost`, אין הערות אדמין, ואין שדה שלא
הוכנס אליו במפורש.** הבידוד מבני ולא הצהרתי: אי אפשר להדליף שדה שלא נכתב שם.

ההיטל **נגזר** (`src/utils/portal.js`) ונכתב אוטומטית בכל שמירה של אדמין
(`useData:withDerived`), וגם **בטעינת האדמין כשיש הפרש** (`App.jsx`). הפרסום
בטעינה אינו נוחות: הנתונים בענן נוצרו לפני שהאוסף היה קיים, ובלעדיו העובד
הראשון שייכנס יראה "לא רשום עליך רכב" והמסקנה תהיה שהפיצ'ר שבור. ההשוואה
עמוקה — אין הפרש, אין כתיבה, אין לולאה. ה-`today` שבחישוב זז פעם ביום, וזה
**רצוי**: החזקה שהסתיימה אתמול מפסיקה להיות קריאה לנהג בלי שאדמין יעשה דבר.

### מה הנהג קורא, ומה חסום מוחלט

| קורא | חסום |
|---|---|
| `driverPortal/{שלו}` | `vehicles` — **גם הרכב שהוא מחזיק** |
| `drivers/{שלו}` (uid, או מייל תואם לפני קישור) | `vehiclesPrivate` · `finesPrivate` · `incidentsPrivate` |
| `assignments` שלו | כל רשומה של נהג אחר, פר-אוסף |
| `fines` שלו · `fineScans` של **הקנסות שלו** | סריקת קנס של **מחזיק קודם באותו רכב** |
| `odometerReadings` שלו | `leaseCompanies` · `documents` · `serviceRecords` · `incidents` |

**כותב:** קריאת מד חדשה לרכב שההיטל שלו מצביע עליו. אין update ואין delete —
דיווח שנשלח הוא רשומה, לא טיוטה; תיקון הוא דיווח נוסף.

### דיווח הק"מ — מה שאין בו הוא התוכן

- **בלי צילום.** לא בגלל ש-Storage אינו פעיל, אלא **כהחלטה**: אין תמונה ⇒ אין
  EXIF ⇒ אין מיקום ואין שעה שהעובד לא התכוון למסור. שדות התמונה בסכימה
  **ננעלו ולא נמחקו** — ב-`createDriverReading`, ב-`isDriverReadingCreate`
  שב-rules, ובסריקת קוד ב-`portal:check`. בלי זה, הפעלת Blaze וחמש-עשרה שורות
  היו מחזירות את כל הווקטור **בלי סקירה**, כי לא נוסף שדה — שדה קיים התמלא.
- **בלי `navigator.geolocation`**, ובלי בורר תאריך.
- **`createdAt == date`** — תאריך, לא חותמת דיוק-שנייה (D4.3). חותמת מדויקת
  מתעדת מתי בדיוק העובד עמד ליד הרכב; זה מעקב אחר עובדים.
- קריאה **נמוכה מהקודמת** מקבלת אזהרה ולא חסימה. מסך שחוסם אותה מלמד את העובד
  שלא כדאי לדווח.

### נרמול גימייל

`a.b@gmail.com`, `ab@gmail.com` ו-`ab+work@gmail.com` הם **אותה תיבה** ושלוש
מחרוזות. ההשוואה עוברת דרך `canonicalEmail` (`utils/admins.js`) ודרך תאומו
`canonEmail` ב-`firestore.rules`. **מוחל רק על gmail.com/googlemail.com** —
בדומיין ארגוני נקודה היא תו משמעותי, ו-`first.last@` אינו `firstlast@`.
ב-allowlist האדמינים ההתאמה היא **raw או canon** — הרחבה בלבד; כלל שמצמצם
גישה קיימת הוא בדיוק הדרך לחזור על באג 17.8.

## חיבור ל-Firebase (אופציונלי)

1. Firebase Console → פרויקט חדש → Firestore ב-**production mode**, region **`me-west1`** (תל אביב).
2. Authentication → הפעל **Google**.
3. Storage → הפעל, אותו region.
4. Project settings → Web app → העתק את הערכים ל-`.env` (לפי `.env.example`).
5. מלא את מזהה הפרויקט ב-`.firebaserc`.
6. `npm run build` — **הערכים נצרבים ב-build**; כל שינוי קונפיג דורש build מחדש.

`.env` **לא** נכנס ל-git. מפתחות ה-Web ציבוריים ממילא — ההגנה האמיתית היא ה-rules.

### כמה מנהלים לאותו צי (`VITE_FLEET_ORG_ID` + `org.adminEmails`)

מזהה הארגון **קבוע בזמן build** — `VITE_FLEET_ORG_ID` — ולא נגזר מהמשתמש
המחובר. כל המנהלים פותחים את **אותו** מסמך `orgs/{id}`, והגישה נקבעת ע"י
**allowlist של כתובות מייל** בתוך המסמך (`org.adminEmails`). זהו הדפוס של
`VITE_CLUB_ID` ב-`Output/basketball-scheduler`, שחי בפרודקשן.

> ⚠️ **הבאג שזה מתקן (17.8.2026).** עד עכשיו `useData.js:63` קבע
> `orgId = user.uid`, כלומר מזהה הארגון היה ה-uid של מי שמחובר. זה עבד בדיוק
> למשתמש אחד — מי שהקים את הארגון — וכל אדמין נוסף נשלח ל-`orgs/{ה-uid שלו}`
> שאינו קיים, וקיבל **מסך הקמה ראשונית**. מנהלת הכספים קיבלה בפועל את המסך
> הזה; אילו השלימה אותו, היה נוצר ארגון שני נפרד עם אפס רכבים.
> **אין הגירת נתונים:** הערך שמוכנס ל-`VITE_FLEET_ORG_ID` הוא מזהה הארגון
> **הקיים**, כך שהרכבים והנהגים נשארים במקומם.

**להוספת מנהל:** הגדרות ← *ניהול מנהלים* ← הוספת כתובת המייל. אחר כך שולחים
לו את הקישור למערכת (המערכת **אינה** שולחת מייל — התוכנית על Spark, אין
Cloud Functions ואין שרת שישלח). מי שנכנס עם חשבון Google של אותה כתובת מקבל
גישת ניהול מלאה. מי שאינו ברשימה מקבל מסך **"אין לך הרשאה, פנה למנהל
המערכת"** — ולא מסך הקמה.

- **כתובות מלאות ומדויקות, מכל ספק.** אין הנחת דומיין ארגוני ואין
  `endsWith('@company.co.il')` — מנהלת הכספים נכנסה דווקא מ-Gmail פרטי.
  הגבלת הדומיין שעדי המליצה עליה (R-b) **אינה ישימה כאן**, וזו סטייה מתועדת.
- **`email_verified == true` נדרש**, ונאכף ב-rules. זו ההגנה שנשארת: בלעדיה
  אפשר להירשם ב-Firebase Auth עם כתובת של מישהו אחר ולהיכנס לצי.
- הרשימה מוחזקת lowercase, בכתיבה ובקריאה, אחרת `Hildav@…` לא יתאים ל-`hildav@…`.
- **אי אפשר להסיר את המנהל האחרון** — ארגון בלי אף מנהל אינו ניתן לשחזור מתוך
  האפליקציה. נאכף גם ב-`firestore.rules` (`adminEmails.size() >= 1`).
- **הגבול:** ה-allowlist הזה הוא **למנהלים בלבד** — קבוצה קטנה ומוכרת. הבידוד
  של הנהגים בפרוסה 2 יישאר **לפי `uid`** (F1 של עדי): שם יושב ה-PII הפרטני
  (קנסות בשם עובד, סריקות, דיווחי ק"מ), ושם החלפת מייל עבודה אינה סיכון מקובל.
- `org.members` (uid→role) נשאר בסכימה ומוכר ב-rules כמסלול **legacy**. הוא
  קיים כדי שה-deploy לא ינעל את המשתמש מחוץ למסמך הארגון הקיים, שנוצר לפני
  17.8 ואינו מכיל `adminEmails`. השמירה הראשונה מוסיפה אותו לרשימה אוטומטית,
  והמסלול הזה מאבד רלוונטיות.

### בדיקת מסלול הענן מקומית (אמולטור) — בלי לגעת בפרויקט אמיתי

מסלול הענן המלא (התחברות → *אין עדיין ארגון* → הקמה → נתונים חיים) הוא בדיוק
המקום שבו התחבא באג הפרודקשן של 16.8, והוא לא היה ניתן לבדיקה בדפדפן. עכשיו כן:

```powershell
$env:JAVA_HOME = "C:\Program Files\Eclipse Adoptium\jdk-21.0.12.8-hotspot"
$env:PATH      = "$env:JAVA_HOME\bin;$env:PATH"
firebase emulators:start --only firestore,storage,auth --project fleet-rules-test

# בטרמינל שני:
$env:VITE_FB_USE_EMULATOR = "1"
npm run dev
```

במצב הזה האפליקציה מדברת עם האמולטור בלבד (Firestore 8080 · Auth 9099 ·
Storage 9199), ובמסך הכניסה מופיע כפתור **"אמולטור: כניסה כמשתמש חדש
(אנונימי)"** — כל לחיצה נותנת uid חדש, כלומר משתמש שאין לו עדיין ארגון.

- הדגל נקרא בזמן build (`__FLEET_DEV_EMULATOR__` ב-`vite.config.js`) ורק ב-
  `vite serve`. בכל `npm run build` הוא `false` מילולי — הכפתור והחיבור
  לאמולטור לא קיימים בפרודקשן. אומת בהרצת `npm run preview` על ה-build.
- **אין צורך ב-`.env.local`** — משתנה סביבה מספיק. `.env.local` עם קונפיג
  ריק ששוכחים למחוק = build בלי ענן שנראה כמו אובדן נתונים.

### מה עדיין חסום ⛔

- **G1 — היידוע לעובדים לא נמסר ולא תועד.** זה החוסם שנשאר, והוא **ארגוני ולא
  הנדסי**: 0 מתוך 29 העובדים עם `notice.acknowledgedAt`, ו-`POLICY_VERSION`
  מצביע על מסמך שאינו קיים. M4 הופך אותו לחסימה אמיתית בקוד — אין מסירת הודעת
