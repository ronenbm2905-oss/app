## ⛔ B1 — מחיקת כפילות שולחת למאמן **`ביטול אימון`** על אימון שממשיך להתקיים

**זה החוסם היחיד, והוא לא בשדה החדש ולא באישור — הוא בכפתור שמעליו.**

`DuplicateRows` ב-`HallClashesCard.jsx:110` ו-`:205`:

```js
const dropOne = (g) => save(withoutSessions(data, g.dropIds));
```

`withoutSessions` מחזיר מערך `sessions` **חדש**. ולכן ב-`withChangeLog`
(`scheduleChanges.js:246`) התנאי `prev?.sessions === next.sessions` אינו מתקיים,
`diffSessions` רץ, ו-`prev.forEach` ב-`:136-138` מוצא ש-`s2` נעלם:

```js
prev.forEach((s, id) => {
  if (!next.has(id)) out.push(entry(s.coachId, "removed", s, { before: shape(s) }));
});
```

`kind: "removed"` → `changeKindLabel:342` → **`ביטול אימון`** → `changeDetail:369-372` →
**`יום שני 12.10 · 17:00–18:30 · רימונים`**. עקבתי עד הסוף: `stillAhead` **אינו** מסנן
אותה (כפילות מדווחת רק קדימה — `duplicateSessions.js:58`), ו-`severity` ב-
`pushTargets.js:138` נותן ל-`removed` משקל **1 מתוך 6** — כלומר באצווה היא גם זו
**שתיבחר להיאמר בשם**.

**וזה מה שהמאמן מקבל על מסך הנעילה:**

> **ביטול אימון**
> `יום שני 12.10 · 17:00–18:30 · רימונים`

**האימון הזה לא בוטל.** השורה התאומה — זהה בקבוצה, במאמן, באולם, בשעות, בשבוע ובסוג —
**נשארה על הלוח**. מחקנו עותק כפול; אמרנו לו שהאימון בוטל.

### למה זה חוסם, ולמה אני לא מוכנה לדחות אותו

**(א) זה אינו תרחיש — זו תקלה שכבר קרתה בתיק הזה, והקובץ מתעד אותה במילותיו שלו.**
`scheduleChanges.js:145-148`:

> *"Archiving July on 22.9.2026 removed that month's sessions from the club document, the
> diff below saw eleven deletions, and six coaches were told — on their phones — that a
> training had been cancelled. A training in July."*

**אותה תבנית בדיוק:** פעולה שהיא **ניהול רשומות** ולא שינוי לו״ז, שעוברת ב-diff כמחיקה
ויוצאת כביטול. אז התיקון היה **סינון בנקודת הרישום** (`stillAhead`). כאן צריך בדיוק את
אותו דבר, באותו מקום.

**(ב) זה דיבור, לא שתיקה — וכל מבנה ההגנה של התיק מגן על שתיקה.** §2ז ("אין בכך
התחייבות שכל שינוי יפיק הודעה") ו-§5 ("אין להסתמך על היעדר התראה") מגנים על **אי-שליחה**.
כאן הפרענו למאמן ו**אמרנו לו דבר שאינו נכון**. זו ההבחנה שעליה חסמתי ב-B1 של #27
וב-B2 של #28, ואיני יכולה להחיל אותה פעמיים ביום ולהתעלם ממנה בשלישית.

**(ג) כיוון הטעות הוא הבלתי-הפיך.** זו האסימומטריה שרונן עצמו ניסח הבוקר ושאימצתי בשער
#27: מאמן שלא יודע על תזוזה מגיע בשעה הלא נכונה; **מאמן שחושב שהאימון בוטל — לא מגיע.**
ואז יש ילדים באולם בלי מאמן. ההשמטה אינה הפיכה.

**(ד) והשער הזה הוא מה שהופך את זה מחוב רדום לפעולה שגרתית.** הכפתור הגורף
(`נקה את כולן`) קיים מלפני היום — אבל הוא שואל שאלה, והוא מעולם לא הופעל על נתונים
אמיתיים (רונן מדד 0 כפילויות). השער הזה מוסיף כפתור **פר-שורה, בלי שלב אישור**, וההערה
בקוד (`:172-174`) מנמקת במפורש למה לא. **הנימוק נכון ביחס למחיקה; הוא לא לוקח בחשבון
שהמחיקה מצפצפת בטלפון של מישהו.** ברגע שרונן ינקה עשר כפילויות, עד עשרה מאמנים יקבלו
`ביטול אימון` על אימונים שמתקיימים.

> **תנאי שחרור — כעשר שורות, בנקודת הרישום, ולא בנקודת השליחה:**
>
> שורה שנמחקה ו**נשארה שורה זהה לה** אינה מחיקה שהמאמן יכול או צריך לפעול לפיה.
> ב-`diffSessions`, בלופ המחיקות:
>
> ```js
> // A ROW REMOVED WHILE AN IDENTICAL ONE SURVIVES IS NOT A CANCELLATION.
> //
> // De-duplicating the board deletes one of two rows that are the same row — same team,
> // coach, hall, day, hours, type and week. Nothing about the coach's Monday changed, and
> // yet the diff sees a deletion and `changeKindLabel` reads it out as "ביטול אימון".
> // The coach is told a training is off while it is still standing, and a coach who
> // believes that does not come. This is the 22.9.2026 archiving failure in a new place:
> // record-keeping passing through the diff as a schedule change. Filtered at the point of
> // RECORDING, like `stillAhead`, because an entry nobody can act on is not worth a slot
> // in a log capped at 150.
> const twin = new Set([...next.values()].map((s) => `${str(s.weekOf)}|${sessionKey(s)}`));
> prev.forEach((s, id) => {
>   if (next.has(id)) return;
>   if (twin.has(`${str(s.weekOf)}|${sessionKey(s)}`)) return;
>   out.push(entry(s.coachId, "removed", s, { before: shape(s) }));
> });
> ```
>
> `sessionKey` הוא **בדיוק** אותה הגדרה שעל פיה הכפילות אובחנה (`rowCopy.js:33`) — ולכן
> הסינון מכסה את מה שהכפתור מוחק, לא יותר ולא פחות. מחיקה **אמיתית** של אימון (אין תאום)
> מדווחת כרגיל.
>
> **ובדיקה שנועלת, אחרת זה יחזור בגרסה הבאה:**
> ```js
> t("DELETING A DUPLICATE IS NOT A CANCELLATION — an identical row is still standing", () => {
>   const before = data.sessions;                       // s1 and s2 are the same row twice
>   const after  = withoutSessions(data, ["s2"]).sessions;
>   assert.deepEqual(diffSessions(before, after, NOW), [], "no entry, therefore no push");
> });
> t("and deleting the LAST one is still a cancellation", () => {
>   const after = withoutSessions(withoutSessions(data, ["s2"]), ["s1"]).sessions;
>   const out = diffSessions(data.sessions, after, NOW);
>   assert.equal(out.length, 1);
>   assert.equal(out[0].kind, "removed");
> });
> ```
>
> **🟢 S1 (אותו שורש, הכיוון ההפוך, לא חוסם):** הוספת שורה כפולה מפיקה `אימון חדש`
> על אימון שהמאמן כבר מחזיק. אותו `twin` פותר גם את זה בלופ ההוספות. **לא חוסם** —
> "משהו נוסף" שגוי מוביל להגעה, לא להיעדרות.

## תשובות לחמש השאלות

### שאלה 1 — מה נשמר, והאם זה מצריך שורה בנוהל המחיקה: **ההכרעה שלך נכונה בעיקרה, ושני פרטים בה אינם.**

**קודם התשובה כפי שנשאלה, והיא מקלה ועומדת:** **לא, `acceptedChecks` אינו מצריך שורה
בטבלת הפתיחה של נוהל המחיקה, ואינו מצריך סעיף משלו.** בדקתי את התקדים בקובץ עצמו, והוא
חד: טבלת הפתיחה ו-§§6-14 מונים **רשומות שיש בהן מידע על אדם** או מסמכים שיש להם תקופת
שמירה נפרדת. ולעומת זאת `fixedWeekSkips`, `hideFixedTeams`, `archivedMonths`,
`notifyPausedUntil`, `departBeforeMin` ו-`schedulePublished` — **אף אחד מהם אינו מופיע
בנוהל, ולו פעם אחת.** `acceptedChecks` הוא מאותה משפחה: העדפת תצוגה של מנהל/ת, ולא רשומה
על נושא מידע. **ההיגיון שלך "זו העדפת תצוגה" הוא ההיגיון הנכון, ואני מאשרת אותו.**

**ומה שכן — ושני אלה אינם ניסוח:** ⟶ **M1** ו-**M2** להלן. אחד מהם סותר במפורש את המשפט
שכתבת ("אין שם אדם"), והשני הוא נתיב שכבר יש לו נוהל בתיק הזה.

#### 🟠 M1 — "אין בו שם אדם" אינו נכון: המפתח נושא את `type`, ואחד מערכיו הוא **`יורם`**

**זה הממצא שאני מבקשת שתקרא לאט, והוא בדיוק בשדה שהבדיקה מתיימרת לנעול.**

מפתח הכפילות הוא `weekOf|sessionKey(s)`, ו-`sessionKey` (`rowCopy.js:33`):

```js
return [s.teamId, s.coachId, s.hallId, s.day, s.start, s.end, s.type || ""].join("|");
```

כלומר הסגמנט האחרון הוא **`type` כפשוטו**. ו-`SESSION_TYPES` (`constants.js:22-29`)
הוא רשימה סגורה של שישה ערכים, ובהם:

```js
{ id: "יורם", name: "יורם", color: "#CA8A04" },
```

**`יורם` הוא שם פרטי של אדם** — מאמן/מדריך של המועדון, והתיק יודע זאת: `scheduleChanges.js:297`
כותב במילותיו *"`type` also carries 'יורם' and 'חד״כ' — training variants in this club"*.
ולכן מפתח אמיתי לחלוטין נראה כך:

```
2026-10-11|t1|c1|h1|שני|17:00|18:30|יורם|x2
```

**ובמקביל:** המפתח נושא גם את **`day` כמחרוזת עברית** (`שני`) — לא מזהה ולא שעה. גם זה
אינו "ids and clock times".

**שלוש הצהרות מתיישנות איתו, ושתיהן בקוד שאתה כותב היום:**

| מקום | מה כתוב | מה לא נכון |
|---|---|---|
| `acceptedChecks.js:14-16` | *"built from ids and clock times — team id, coach id, hall id, hours — and carries no name of a person"* | **`type` ו-`day` אינם במניין; `type` יכול להיות שם פרטי** |
| `constants.js:85-87` | "Keys only — week, team id, coach id, hall id, hours — never a name" | אותו דבר |
| הבקשה שלך אליי, סעיף 1 | "אין שם אדם, קבוצה או אולם" | **קבוצה ואולם — נכון. אדם — לא** |

**ועכשיו החלק שמטריד אותי יותר מהניסוח: הבדיקה שאתה מצביע עליה כנועלת את זה —
אינה נועלת אותה.** `duplicatesessions.test.mjs:200-209`:

```js
for (const name of ["ילדים ב", "עומר", "סהר", "רימונים"]) {
  assert.equal(key.includes(name), false, name);
}
```

**לאף אחת מארבע רשומות ה-fixture בקובץ אין `type` כלל** (`:26-31`) — ולכן
`s.type || ""` מחזיר מחרוזת ריקה, והסגמנט שבו הבעיה יושבת **לא נבדק אפילו פעם אחת**.
הבדיקה עוברת על היעדרות, לא על נוכחות. **זו בדיוק M6 של שער #13** — הממצא החד ביותר שם:
בדיקת מזעור שעברה על מחרוזת ריקה. אני מבקשת שלא נחזור עליו שבועיים אחרי שנסגר.

> **מה אני מבקשת — ולא מה שאולי נראה מתבקש:**
>
> **אני לא מבקשת להוציא את `type` מהמפתח.** הוא שם בצדק: `אימון` שהפך ל-`משחק בית`
> הוא לא אותה שורה, ואם המפתח יתעלם ממנו, אישור על כפילות אימונים יכסה בשקט כפילות
> משחקים. **הזהות של הבדיקה חייבת להישאר זהה ל-`sessionKey`**, וההנמקה שלך ב-
> `duplicateSessions.js:14-17` נכונה ואני מאמצת אותה.
>
> **וגם לא מבקשת סעיף בנוהל המחיקה בגלל `יורם`.** המחרוזת `יורם` **מופיעה ממילא בקוד
> המקור בריפו ציבורי**, היא מוצגת לכל מאמן על הלוח, והיא סוג-מפגש ולא רשומה על אדם.
> **אין כאן קטגוריית מידע חדשה, אין נושא מידע חדש, אין נתיב גישה חדש ואין אירוע לפי
> תקנה 11.** חסימה כאן תהיה המצאת חובה שאינה קיימת, ואני לא עושה את זה.
>
> **מה שאני כן דורשת זה שני דברים, ושניהם זולים:**
>
> **(1) שההצהרה תתאר את מה שנשמר, ותישאר נכונה כשהרשימה תגדל.** המניין החיובי מתיישן;
> העיקרון השלילי לא — אותה אסימטריה בדיוק שאישרתי ב-M6 של שער #27:
>
> > `// WHAT IS STORED IS A KEY, NEVER A ROW. A key is built from the week or date, the ids`
> > `// of the team, coach and hall, the day name, the clock times, and the session TYPE —`
> > `// which in this club is a closed list that includes "יורם", the first name of one of`
> > `// its trainers. So: no player, no phone, no free text, nothing about a child, and`
> > `// nothing that is not already on every coach's board — but do not write "no name of a`
> > `// person" here, because that is the sentence that went stale.`
>
> וב-`constants.js:85-87` — אותו תיקון בקצרה.
>
> **(2) שהבדיקה תבדוק את הסגמנט שבו הבעיה.** שורה אחת:
> ```js
> T("the stored key carries the session TYPE, which in this club can be a first name", () => {
>   const d = { ...data, sessions: data.sessions.map((s) => ({ ...s, type: "יורם" })) };
>   const key = acceptKeyOf(duplicateSessionGroups(d, { from: BEFORE })[0]);
>   assert.ok(key.includes("יורם"), "deliberate — identity must match sessionKey exactly");
>   // And what must NEVER be in it, on a fixture that actually has the fields:
>   for (const banned of ["ילדים ב", "עומר", "סהר", "רימונים"]) {
>     assert.equal(key.includes(banned), false, banned);
>   }
> });
> ```
> **שימי לב שהבדיקה הזו מאשרת את הנוכחות ואוסרת את האחרות** — זו הצורה הנכונה, כי
> המטרה אינה "אין מחרוזות" אלא "אנחנו יודעים בדיוק אילו".

#### 🟠 M2 — המפתח נושא `coachId`, ו-§4 (עזיבת מאמן) **אינו יודע עליו** — וה-gc אינו ללא-תנאי

שני הפרטים האלה נכונים רק יחד, ולכן הם ממצא אחד.

**הראשון:** לשדה על `clubs/main` שנושא `coachId` **יש תקדים מפורש בתיק** — §6.2 בנוהל
המחיקה: *"עזיבת מאמן/ת: למחוק את כל הרשומות שבהן `coachId` הוא שלו/ה, **לפני** מחיקת
המאמן"* — ו-§6.2 מוסיף שהמסך **אוכף** את הסדר. `acceptedChecks` נושא `coachId`,
ו-`coachUsage` (שחוסם מחיקת מאמן) **אינו יודע עליו**. כלומר: מאמן עוזב, §4 מורץ במלואו,
והמפתח עם ה-`coachId` שלו נשאר במסמך.

**השני — וזו הסיבה שאני לא דורשת סעיף בנוהל:** `pruneAccepted` **כן** פותר את זה,
אבל רק אם הוא רץ. והיום הוא רץ **רק מתוך `accept`** (`acceptedChecks.js:62`) —
